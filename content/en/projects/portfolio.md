Most developer portfolios are a résumé wearing a website's clothes: a static page that lists jobs and skills and hopes a recruiter reads far enough to notice the person behind it. That was the starting problem — a portfolio that looked like every other portfolio, saying nothing about how its author actually works.

The goal here wasn't to build a bigger brochure. It was to build a small product with the same discipline as a real one, and let the site itself be the evidence: real internationalization instead of a language toggle bolted on later, a documented architecture instead of tribal knowledge, an automated release pipeline instead of hand-typed version bumps, and content that lives in data files instead of hardcoded strings scattered across components — so the site can grow the way a real codebase grows, not the way a static page gets patched.

The inspiration was practical more than aesthetic: every choice made here — the locale routing, the dictionary-driven text, the CI gates, the conventional commits feeding an automated changelog — is a choice a hiring team would recognize from a production codebase, because it's built the same way. The coding-time and language metrics on this very page aren't decorative; they're pulled live from the tools that were actually used to build it, so the story the site tells about its own construction is provable rather than asserted.

As a portfolio, there's admittedly not much of a "problem domain" to solve — no users to onboard, no business rule to enforce. What's worth capturing instead is the shape of the process: this project exists as the first entry and the working template for the ones that follow it. Every future project added here should be able to point back to this one and say, this is the bar — documented, internationalized, measured, and honest about what it is.
